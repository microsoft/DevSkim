# Kubernetes Container Allows Privilege Escalation

## Summary

* A container does not set `allowPrivilegeEscalation` to `false`, either because it is `true` or
  because the field is omitted and Kubernetes defaults it to `true`.
* Set it to `false`. The Restricted Pod Security Standard requires this.

## Details

`allowPrivilegeEscalation` controls the `no_new_privs` flag on the container process. When it is
true, a process can end up with more privileges than the process that started it, through:

* **setuid and setgid binaries.** A binary in the image owned by root with the setuid bit set will
  run as root even though the container started as an unprivileged user.
* **file capabilities.** A binary carrying capabilities in its extended attributes gains them on
  exec, regardless of the calling process's own set.

This matters most in exactly the case where the other controls appear to have been applied. A
container running as uid 10001 with a dropped capability set looks constrained, but if the image
contains a setuid root binary, an attacker with code execution can still become root inside the
container and then attack whatever the container can reach.

Note that setting `privileged: true` forces `allowPrivilegeEscalation` to true regardless of what
you write here.

### What this rule can and cannot tell you

An explicit value other than `false` is reported on the container that sets it, regardless of the
other containers in the file. An omitted field is reported against each container, but the engine
can only evaluate that omission over the whole file, so it is not reported once any container in
the manifest sets `allowPrivilegeEscalation`. Treat a clean result as "every container that sets the
flag sets it to `false`", not as proof that every container sets it.

## Solution

``` yaml
securityContext:
  allowPrivilegeEscalation: false
  runAsNonRoot: true
  runAsUser: 10001
  capabilities:
    drop:
      - ALL
```

Combine it with a seccomp profile, which the Restricted standard also requires:

``` yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

Enforce the Restricted profile at the namespace level rather than relying on each manifest to set
the field correctly.

## Severity Considerations

Raise the severity when the image is built from a general-purpose base image, since those commonly
carry setuid binaries such as `mount`, `su` and `ping`. A distroless or scratch image with no setuid
binaries reduces, but does not remove, the concern.
